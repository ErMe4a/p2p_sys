## 7. Celery — архитектура очередей и хронический затор

**Задача:** обнаружен хронический затор очереди `sync` (изначально 277+, позже вновь найдено 218 застрявших task'ов).

**Корневая причина (найдена и подтверждена):** в vendored `bybit_p2p/_p2p_manager.py`, `_send_request()` не имел `timeout=` у `requests` — любой сетевой глюк Bybit вешал воркер навсегда, задачи копились.

**Решение и сделано:**
- Добавлен `timeout=30` в `_send_request`.
- `sync_bybit_orders_task` переделан в диспетчер (fan-out) → по одной задаче на каждого из 85 Bybit- и 62 MEXC-юзеров вместо одного большого последовательного цикла.
- `recheck_mexc_keys_task` перенесена с очереди `sync` на `receipt` — и в коде (`@shared_task(queue=...)`), и в БД (`django_celery_beat.PeriodicTask.queue`, отдельно — код не перекрывает то, что явно задано в БД).
- После деплоя обнаружен ожидаемый временный всплеск: 218 старых зависших task'ов, размножившись под новым (fan-out) кодом, разово создали ~18 000 подзадач в очереди — очередь вычищена командой `celery -A core purge -Q sync -f` (осознанно, т.к. синк идемпотентен, ничего не потеряно).
- Финальная проверка: `sync: 0`, `receipt: 0` — здорово.

**Осталось:** сама причина хронического затора в очереди `sync` до этого фикса (были ли там ещё скрытые проблемы, кроме таймаута) отдельно не расследовалась — раз таймаут-фикс решил проблему на практике, глубже не копали. Уникальные nodename для celery-воркеров (`DuplicateNodenameWarning`) — так и не сделаны, флагнуто ранее, не тронуто.

## 8. "Необработанные ордера" — полный разбор процесса и улучшения

**Задача:** Макс попросил разобрать весь процесс необработанных ордеров целиком и понять, насколько он оптимален.

**Найденные проблемы и решения:**

1. **Гонка (race condition):** синк снимает "снимок уже обработанных" в начале, ордер мог зафискализироваться через расширение, пока синк ещё работал (постранично тянет с биржи) → синк вставлял его обратно в `UnprocessedOrder` уже после того, как штатное удаление отработало. **Сделано:** самоисправляющаяся подчистка в конце `sync_bybit_orders`/`sync_mexc_orders` — если для юзера в `UnprocessedOrder` есть строка, для которой уже есть реальный `Order`, удаляется. Разово почищен и накопленный бэклог (было 523 → сейчас единицы).
2. **Отсутствие пагинации** на странице "Необработанные" — у некоторых юзеров тысячи строк (до 4221 у одного). **Сделано:** пагинация по 200.
3. **Фильтр по бирже** — добавлен (с гарантированными Bybit/MEXC в списке всегда, даже если у юзера сейчас там пусто).
4. **Массовое игнорирование** — чекбоксы + "выбрать всё на странице" + кнопка с подтверждением, ограничено размером страницы (без риска случайно снести тысячи строк одним кликом).
5. **Мёртвый код** `next_sync_ts` (считался на каждый заход на страницу, нигде не использовался) — убран.
6. **Индикатор очередей Celery** (sync/receipt/celery) добавлен в админку (`users_list.html`) — раньше затор обнаруживали только руками через `redis-cli`.
7. **Двойной запрос к API биржи** (при синке и при верификации перед чеком) — разобрано, признано осознанной защитой (не фолбэк на устаревшие данные), НЕ убрано. Вместо этого сделана "подсказка" (`hint`) — см. §10.

**Осталось:** ничего критичного не осталось открытым; корневая причина затора очереди `sync` относится к §7 (та же сессия работы).

## 9. Дата ордера — берём из API биржи, а не с момента "пробития"

**Задача:** у пользователей на странице Bybit при пробитии ордера иногда возникала ошибка "не удалось определить дату создания заказа" — расширение парсило дату со страницы (хрупкий DOM-парсинг), и парсинг иногда ломался.

**Решение (подтверждено реальным запросом к Bybit API — поле `createDate` в `get_order_details` реально существует и корректно парсится):**

- Расширение (`content.js`) перестало жёстко блокировать отправку при отсутствии даты со страницы — просто не шлёт `createdAt`, сервер сам подставит из API.

**Сделано.** Задеплоено и подтверждено сравнением реального ответа Bybit API с локальным расчётом.

## 10. "Подсказка" (hint) из Необработанных для предзаполнения формы расширения

**Задача (по итогам §8, п.7):** избежать дублирования данных между синком и верификацией хотя бы частично — на UX-уровне.

**Решение:** `GET /api/order` мог бы отдавать `hint` (price/amount/quantity/type) из `UnprocessedOrder`, если реального `Order` ещё нет — расширение использует это для быстрого предзаполнения формы вместо хрупкого DOM-парсинга. Сама верификация перед чеком остаётся обязательной и не меняется.

**Сделано, а затем ВРЕМЕННО ОТКАЧЕНО на сервере:**
- Реализовано в `api_views.py`, `content.js`, `mexc.js`, `order_api.js` (версия расширения 1.4.8, зип собран).
- **Откачено** серверное изменение (`api_views.py` вернули к исходному 404-based ответу) — потому что пока пользователи на старом расширении 1.4.7, у MEXC свой кастомный `checkOrderExists`, который считал "ордер существует" просто по факту HTTP 200 — новый бэкенд (всегда 200) сломал бы это ещё до раздачи нового расширения.
- Заготовка 1.4.8 осталась в коде расширения (и её же сделали устойчивой к обоим вариантам ответа сервера — определяет наличие поля `exists`, а если его нет — откатывается на старую эвристику).

**Осталось:** когда 1.4.8 реально раздадут пользователям — вернуть в `api_views.py` GET-хендлер блок с `exists`/`hint` (сохранён в истории разговора/гита). Пока — не трогать.

## 11. Час "Сегодня" в личном профите — таймзона и обнуление остатка

**Задача 11а:** вкладка "Сегодня" в `/profit/` считала границы суток по UTC, а не МСК — сделки с полуночи до 3:00 МСК попадали в "вчера", и наоборот.

**Сделано:** `get_turnover` (views.py) теперь переводит `timezone.now()` в МСК ПЕРЕД тем, как обнулять часы.

---

**Задача 11б (более серьёзный баг, найден по жалобе Макса на юзера maslennikov):** "Текущий остаток" показывал 0, хотя реальный остаток (покупки минус продажи) был 4532 USDT.

**Причина:** `_calc_currency_from_orders` группирует ордера по месяцам и ищет "целевой" месяц; если у юзера в запрошенном периоде (например "сегодня"/этот месяц) вообще нет ни одного ордера — цикл проходил все прошлые месяцы, копил перенос (`prev_carry`), но `is_target` не срабатывал ни разу → функция проваливалась в аварийный `if result is None:`, который **обнулял всё**, выбрасывая уже посчитанный перенос.

**Сделано:** при аварийном случае остаток берётся из последнего накопленного `prev_carry`, а не обнуляется. Проверено на реальных данных (0.0 → 4532.56).

**Расследование:**

- Оригинальные загруженные Excel-файлы (например `simonenko.xlsx`) **нигде не сохраняются** — читаются "на лету" из памяти и выбрасываются сразу после подсчёта итогов. Восстановить их для полноценного построчного импорта неоткуда — нужно искать оригинал у Макса/бухгалтера.

Требует точного знания всех нужных колонок в "строках ордеров" оригинального файла.
2. Проще — не трогать построчный импорт, просто подставлять итоговую строку `MonthlyManualEntry` за январь ОДНОЙ строкой в начало `export_excel_report` (без детализации по сделкам).

## 19. Прочее (упомянуто, не требует действий)

- **nginx `/tmp_downloads/`** — пользователь самостоятельно удалил директорию `/var/www/html/tmp_downloads` и убрал соответствующий `location` из конфига nginx (был разовый ручной механизм раздачи файлов в обход Django, в коде проекта нигде не упоминался — чистка безопасна, ничего не сломает).
- **Ошибка "не транспортный контейнер"** при попытке юзера напрямую залить наш сырой XML НДС/уведомления на сторонний портал приёма отчётности — объяснено: наши XML нужно сначала провести через ПО для сдачи отчётности (Астрал Отчёт и т.п.), которое подписывает и упаковывает в транспортный контейнер — это не баг, а неверный порядок действий у пользователя.
