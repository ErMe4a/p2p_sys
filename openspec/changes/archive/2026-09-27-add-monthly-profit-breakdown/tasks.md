## 2. Расчёт и кэширующая Celery-задача

- [x] 2.1 Вынести переиспользуемый помесячный расчёт по всем пользователям в отдельную функцию (если ещё не
      выделена) — единая точка, которую использует и обычная страница «Прибыль» за один месяц, и новая задача,
      чтобы оба места гарантированно давали одинаковые числа (см. spec.md "Расчёт согласован с помесячной
      страницей").
      → Реализовано как новая функция `_calc_all_users_month_profit()` (views.py), а не рефактор существующего
      цикла `admin_profit_view` — она вызывает те же module-level функции (`_calc_month_profit_from_orders`,
      `_calc_ndfl`, `_get_ytd_base_from_cache`) и copy-точно повторяет ту же формулу gross/net/share, но не
      трогает уже рабочий код `admin_profit_view` (сознательное решение — нулевой риск регресса на
      финансово-критичной живой странице; см. докстринг функции).
- [x] 2.2 Написать `recompute_yearly_profit_summary_task` (`orders/tasks.py`, `queue="receipt"`) — для каждого
      месяца текущего года считает `gross_traders`/`net_traders`/`system_income` по всем пользователям (all +
      usdt + ton), пишет/обновляет `MonthlySystemProfitSummary` (`update_or_create`).
- [x] 2.3 Проверить время выполнения задачи на реальных данных прод-БД (ожидание — сопоставимо с ~10 сек x 12
      месяцев с учётом фан-аута/оптимизации, не более нескольких минут в фоне).
      → 15.6 сек на весь 2026 год (не минуты) — предзагрузка на весь год одним проходом (а не по месяцу)
      оказалась значительно быстрее худшей оценки из proposal.md.
