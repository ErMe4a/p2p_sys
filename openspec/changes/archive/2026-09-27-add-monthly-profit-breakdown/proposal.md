## Why

Вкладка «2026» в админской «Прибыли» (`custom_admin/profit_year.html`) уже показывает оборот (покупки/продажи)
по месяцам за год по всей системе сразу. Максу этого недостаточно — нужна полная картина: сколько система
заработала (доля/чистая прибыль) и сколько заработали трейдеры (грязная прибыль), тоже помесячно за год, не
только по одному месяцу за раз, как сейчас на основной странице «Прибыль».

Задача уже обсуждалась и была приостановлена пользователем («пока тормозни задачу», см. `openspec/history.md`
§38) из-за нерешённого вопроса производительности — нужно сначала формально зафиксировать требования и способ
решения, прежде чем реализовывать.

## What Changes

- Вкладка «2026» дополняется по каждому месяцу: грязная прибыль трейдеров, чистая прибыль трейдеров (после
  налога), доля/доход системы — в дополнение к уже существующим покупкам/продажам/обороту.
- Расчёт по каждому месяцу требует LIFO-себестоимости по каждому из ~142 пользователей (та же логика, что уже
  использует основная страница «Прибыль» за один месяц, ~10 сек на 142 юзерах) — синхронно за 12 месяцев на
  одной странице это ~2 минуты, неприемлемо для HTTP-запроса.
- Способ решения этой проблемы производительности — предмет `design.md` (кандидаты: фоновая Celery-задача с
  кэшем по аналогии с `User.fns_status_cached`, либо дозагрузка по клику на месяц).

## Capabilities

### New Capabilities
- `admin-yearly-profit-summary`: годовая сводка на вкладке «2026» в админской «Прибыли» — оборот, грязная
  прибыль трейдеров, чистая прибыль трейдеров, доход системы, помесячно, по всем пользователям сразу. Формальной
  спецификации на уже существующее поведение (оборот по месяцам) до сих пор не было — эта спека фиксирует его
  целиком вместе с новой частью (прибыль), а не только дельту.

### Modified Capabilities
(нет — оборот по месяцам не описан существующей спекой, поэтому это не изменение существующего требования, а
первая формальная спецификация всей вкладки целиком, см. New Capabilities)

## Impact

- `orders/views.py`: `_year_turnover_by_month()` (существующая, лёгкая), `admin_profit_view()` (роутинг
  `?month=year`) — потребует нового кэширующего механизма и/или фоновой задачи для прибыли.
- `orders/tasks.py`: вероятно новая периодическая Celery-задача (пересчёт кэша), по аналогии с
  `recompute_fns_status_task`.
- `orders/models.py` + миграция: вероятно новая модель/поле для хранения закэшированных месячных сумм (если
  выбран вариант с кэшем, а не live-подгрузкой).
- `orders/templates/custom_admin/profit_year.html`: новые столбцы/карточки в таблице.
- Прод: 142 активных пользователя, диапазон дат — с `SYSTEM_START` (2026-02-01) по текущий месяц.
