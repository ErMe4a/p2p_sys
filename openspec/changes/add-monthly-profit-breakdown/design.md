## Context

Годовая сводка (`custom_admin/profit_year.html`, роутинг `admin_profit_view` с `?month=year`) сейчас считает
только оборот — `_year_turnover_by_month()`, 12 дешёвых SQL `SUM(cost)`-запросов, без обращения к LIFO-логике.

Прибыль (грязная/чистая, доход системы) уже считается в проекте — `_calc_month_profit_from_orders()`, но ТОЛЬКО
по одному месяцу и одному прогону по всем ~142 пользователям за раз (используется на обычной странице «Прибыль»,
~10 сек на 142 юзерах). Прямой перенос этой же логики на 12 месяцев в рамках одного HTTP-запроса даёт ~2 минуты —
неприемлемо (см. proposal.md).

В проекте уже есть прецедент именно этой проблемы — `User.fns_status_cached`: тяжёлый расчёт (построение XML на
всю глубину года) точно так же был вынесен из live-запроса в персистентное поле, обновляемое fan-out Celery-
задачей `recompute_fns_status_task` раз в 5 минут (см. `openspec/history.md` §4, всё ещё актуально в текущем
коде). Выбранное здесь решение — тот же паттерн.

## Goals / Non-Goals

**Goals:**
- Годовая сводка открывается быстро (секунды), независимо от стоимости расчёта прибыли.
- Прибыль/доход системы по месяцам считаются той же LIFO-логикой, что и остальная система (никакого отдельного
  упрощённого расчёта, который может разойтись с помесячной страницей по одному пользователю).
- Админ видит, насколько свежие цифры прибыли (в отличие от оборота, который всегда live).

**Non-Goals:**
- Не даём мгновенный (live, по клику) пересчёт прибыли на этой сводке — сознательно отложено на будущее
  (см. Open Questions), в этой итерации только фоновый кэш.
- Не переделываем сам алгоритм `_calc_month_profit_from_orders` — переиспользуем как есть.
- Не кэшируем оборот — он и так дешёвый, остаётся live-запросом, как сейчас.

## Decisions

**1. Кэш в отдельной модели, не в JSON-поле на User.**
Прибыль считается по системе в целом (сумма по всем юзерам за месяц), а не по одному юзеру — значит это не
персональное поле пользователя (как `fns_status_cached`), а отдельная сущность `MonthlySystemProfitSummary` с
полями `year`, `month`, `currency` (`'all'|'usdt'|'ton'`, для соответствия уже существующему переключателю
валюты на странице), `gross_traders`, `net_traders`, `system_income`, `updated_at`. Уникальность —
`(year, month, currency)`.
_Альтернатива:_ одна широкая строка на месяц (без разбивки по валюте) — отклонено, страница уже умеет
переключать USDT/TON/Все на лету по существующим данным оборота, разбивка нужна и для прибыли для консистентности
UI.

**2. Периодическая Celery-задача, очередь `receipt` (не `sync`).**
По аналогии с `recompute_fns_status_task` (см. `openspec/history.md` §4/§7) — очередь `sync` исторически
подвержена заторам, `receipt` уже используется для похожей по характеру тяжёлой периодической работы.
Периодичность — раз в час (профит меняется медленнее, чем статус ФНС; секундная свежесть не нужна).
_Альтернатива:_ разовый пересчёт по кнопке "Обновить" вместо периодики — отклонено для первой итерации
(усложняет UX и требует доп. состояния "идёт пересчёт"), можно добавить позже поверх периодики без изменения
специфики.

**3. Переиспользуем существующий `_calc_month_profit_from_orders`, не пишем новый расчёт.**
Задача проходит по каждому пользователю и каждому месяцу года (как уже делает `admin_profit_view` для одного
месяца), суммирует `gross`/`ndfl`/`share`/`net` по всем юзерам в аккумулятор на месяц, пишет в
`MonthlySystemProfitSummary`. Это гарантирует, что цифры на годовой сводке математически совпадают с тем, что
показывает helper-страница по одному пользователю за тот же месяц (это отдельно зафиксировано как требование в
spec.md).

**4. Оборот остаётся live, прибыль — из кэша, на одной странице.**
`admin_profit_view` (`month=='year'` ветка) продолжает звать `_year_turnover_by_month()` как сейчас (дёшево) и
дополнительно читает `MonthlySystemProfitSummary` для колонок прибыли. Если кэш для месяца ещё не посчитан
(например, только что задеплоили) — колонки прибыли показывают явный плейсхолдер ("ещё не посчитано"), не 0
(0 выглядел бы как настоящий результат расчёта).

## Risks / Trade-offs

- **[Устаревшие цифры вводят в заблуждение]** → Показываем `updated_at` кэша прямо на странице ("Прибыль
  обновлена: N мин/ч назад"), как отдельный явный элемент интерфейса, а не только в тултипе.
- **[Тяжёлая периодическая задача создаёт лишнюю нагрузку раз в час]** → Тот же профиль нагрузки, что и у уже
  существующей `admin_profit_view` за один месяц (~10 сек), просто теперь в фоне и на 12 месяцев — фан-аут по
  пользователям (как `recompute_fns_status_task`) снижает пиковую нагрузку на один воркер.
- **[Кэш и живая helper-страница по одному юзеру могут разойтись]** → Оба используют один и тот же
  `_calc_month_profit_from_orders`; расхождение возможно только если данные ордеров изменились между
  пересчётом кэша и обращением к странице — это ожидаемое и допустимое отставание (см. Goals), не баг.

## Migration Plan

1. Миграция: новая модель `MonthlySystemProfitSummary`.
2. Деплой кода задачи + вьюхи/шаблона.
3. Разовый ручной запуск задачи на проде сразу после деплоя (`.delay()` из shell), чтобы кэш не был пустым до
   первого тика периодики.
4. Регистрация периодической задачи в `django_celery_beat` через админку (раз в час) — по существующему
   соглашению проекта: периодика настраивается в БД, не в коде.
5. Откат при проблеме: сама вьюха ветки `month=='year'` — если чтение кэша ломается, деградирует до показа
   плейсхолдера "ещё не посчитано" для прибыли, оборот остаётся рабочим (live-часть не зависит от кэша).
