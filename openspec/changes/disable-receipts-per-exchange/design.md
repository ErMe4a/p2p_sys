## Context

`Exchange` (`orders/models.py`) — каталог для UI-дропдаунов (`/settings/`, `/my-orders/`), уже несёт `is_public`/`is_deleted` и (через `User.allowed_exchanges`) список пользователей, которым видна конкретная приватная биржа. Модель по собственному докстрингу **не связана в БД** с `Order.exchange_type` — это свободное текстовое поле, сопоставление идёт только по строке имени. Ровно так же сегодня работает единственный существующий прецедент отключения чека — хардкод в `receipt_service.create_or_update_and_send_receipt()`:

```python
if 'intelion' in str(getattr(order, 'exchange_type', '')).lower():
    return ReceiptResponse(status="SKIPPED", error_text="Чеки для биржи Intelion отключены")
```

Эта функция — единственная точка входа для отправки чека, вызывается из трёх независимых мест (`api_views.py`, `tasks.py`, `views.py`), см. proposal.md.

## Goals / Non-Goals

**Goals:**
- Дать администратору управлять отключением чека по бирже через UI, без правки кода.
- Не менять поведение расчёта оборота/прибыли — они и так не смотрят на чек (подтверждено чтением кода в рамках explore-сессии).
- Переиспользовать уже существующий UI-паттерн страницы каталога (POST + `action`-диспетчер, тег-лист с автодополнением пользователя).

**Non-Goals:**
- Не мигрируем существующий хардкод Intelion на новый механизм — это отдельная, необязательная уборка, вне рамок этой задачи (риск регресса ради чистоты кода не оправдан здесь).
- Не строим автоматический допробив ранее пропущенных чеков при повторном включении биржи — по решению Максима, это остаётся ручной операцией.
- Не меняем существующий список видимости биржи (`allowed_exchanges`/`is_public`) — список исключений по чеку полностью независим от него.

## Decisions

**Хранение — два новых поля на `Exchange`:**
- `receipts_enabled = models.BooleanField(default=True)` — глобальный флаг.
- `receipt_exception_users = models.ManyToManyField(User, blank=True, related_name='receipt_exception_exchanges')` — список исключений.

Альтернатива (отдельная модель `ExchangeReceiptSetting`) отклонена — избыточно для двух полей, `Exchange` и так уже играет роль конфигурационной записи для биржи (как `is_public`).

**Сопоставление `Exchange.name` ↔ `Order.exchange_type` — точное совпадение без учёта регистра (`iexact`), не подстрока.**
Существующий хардкод Intelion использует подстроку (`'intelion' in ... .lower()`), что at это единственное вхождение — безопасно. Для универсального механизма подстрока рискованна (например, гипотетическая биржа «MEXC-test» ложно попала бы под отключение «MEXC»). Точное совпадение по имени, без учёта регистра, — предсказуемее; ключевой риск (админ переименует биржу в каталоге и связь с реальными `exchange_type` в ордерах молча порвётся) — тот же риск, что уже существует у видимости биржи сегодня, ничего нового не добавляем.

**Место проверки — `create_or_update_and_send_receipt()`, сразу после проверки Intelion, до проверки `is_receipt_blocked` (валюта):**
```python
exchange = Exchange.objects.filter(name__iexact=order.exchange_type, is_deleted=False).first()
if exchange and not exchange.receipts_enabled and not exchange.receipt_exception_users.filter(pk=order.user_id).exists():
    return ReceiptResponse(status="SKIPPED", error_text=f"Чеки для биржи {exchange.name} отключены администратором")
```
Один `if`, один запрос (с `select_related`/`prefetch` не требуется — единичная выборка на вызов), автоматически покрывает все три пути отправки чека без их правки.

**UI — новая кнопка рядом с существующими, новый блок исключений визуально отделён от блока видимости:**
Переиспользуем существующий паттерн `action`-диспетчера POST на странице каталога (`toggle_exchange_public` → добавляем `toggle_exchange_receipts`, `add_receipt_exception_user` / `remove_receipt_exception_user` по образцу уже существующих обработчиков видимости). Кнопка подписывается «Отключить чек» / «Включить чек» (не «приватная»/«публичная», чтобы визуально не путать с видимостью). Блок исключений — свой тег-лист под кнопкой, с явной подписью («Кому чек всё равно бить»), отдельно от существующего блока видимости.

## Risks / Trade-offs

- **[Риск] Расхождение имени в каталоге и реального `Order.exchange_type`** (админ переименовал/опечатался) → биржа тихо не подпадёт под отключение. Митигация: тот же риск уже принят проектом для видимости бирж, отдельно не решаем в этой задаче.
- **[Риск] Администратор забудет, что для биржи стоит отключение, и не поймёт, почему у трейдера нет чека** → митигация: `error_text` на пропущенном чеке явно называет причину («отключены администратором»), как и у Intelion сегодня — тот же паттерн диагностируемости.
- **[Компромисс] Нет автоматического допробива при включении биржи обратно** — сознательный выбор (проще, предсказуемее, соответствует текущей ручной практике разбора зависших чеков), но означает, что администратору нужно самому найти и допробить пропущенные ордера после реактивации.

## Migration Plan

Одна миграция Django (новое поле + M2M на `Exchange`, оба с безопасными дефолтами — `receipts_enabled=True` не меняет поведение существующих бирж, `receipt_exception_users` пуст). Обратной совместимости: деплой — `git pull` → `migrate` → `restart p2p` (правка в `receipt_service.py`, который также импортируется в `tasks.py`, поэтому дополнительно `restart celery*`).
