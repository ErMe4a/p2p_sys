## Context

Мотивация описана в proposal.md, требования — в specs/obds-attachments/spec.md.

Что уже есть:
- `ObdsRecord` и блок «База данных ОБДС» на странице «Документооборот» (`admin_obds`, POST-форма);
- форма `obds_request` с полем `request_number` и генератор `orders/documents` (`fill_docx`, `docx_to_pdf` через
  LibreOffice);
- media-хранилище — Yandex S3 (`S3Storage`, `AWS_S3_FILE_OVERWRITE=False`). Публичность объектов зависит от
  бакета, поэтому файлы читаем через storage API и отдаём своим view.

В шаблоне `obds_request.docx` раздел «Приложения:» — один абзац нумерованного списка (`numId=2`) с текстом
«Решение ЦБ от отказе в исключении данных из базы.», а REQ уже подставляется токеном `{{REQUEST}}`.

## Goals / Non-Goals

**Goals:**
- Несколько REQ и решений в одном документе.
- Один PDF «обращение + решения».

**Non-Goals:**
- Включение PDF сделок в документы: придёт со следующими формами, сейчас только хранение.
- Предпросмотр файлов в браузере, версии файлов, загрузка картинок (только PDF).

## Decisions

### 1. Модели
- `ObdsDecision`: `user` (FK, `CASCADE`, `related_name='obds_decisions'`), `req_number` (`CharField(100)`,
  верхний регистр), `file` (`FileField(upload_to='obds/decisions/%Y/%m/')`), `original_name`, `uploaded_at`.
  `unique_together (user, req_number)`. Повторная загрузка: старый файл удаляется из хранилища, объект
  обновляется.
- `ObdsRecord.attachment` (`FileField(upload_to='obds/deals/%Y/%m/', blank=True)`) + `attachment_name`.

Удаление записи или решения удаляет и файл: явный `file.delete(save=False)` в view. Сигналы не используем,
чтобы не было скрытой логики. Файлы при каскадном удалении пользователя не чистятся, это осознанно: пользователей
не удаляют.

Альтернатива — общая модель «файл ОБДС» с типом. Отклонена: у решения уникальность по REQ, у записи — 1:1,
отдельные поля проще.

### 2. Валидация файла
Расширение `.pdf`, первые байты `%PDF-`, размер ≤ 20 МБ. Иначе — `messages` с тегом `obds`.

### 3. Скачивание
`admin_obds_file?kind=decision|deal&id=…` (только суперпользователь): `FileResponse(storage.open(...))` с
`Content-Disposition: attachment` и именем `original_name`.

### 4. Повтор абзаца приложений в шаблоне
В `obds_request.docx` абзац приложения превращается в токен `{{APPENDIX}}`, текст «от отказе» из шаблона
Максима заменяется на «об отказе» (опечатка, отмечаем в отчёте). `fill_docx` получает поддержку списков: если
значение токена — `list[str]`, абзац `<w:p>`, содержащий токен, копируется на каждый элемент (пустой список →
абзац с исходным текстом шаблона, задаётся в форме как fallback). Из копий убираем `w:numPr`, чтобы не было
двойной нумерации «1. Приложение №1». Текст строки: «Приложение №N: Решение ЦБ об отказе в исключении данных
из базы (REQ-…)».

Альтернатива — переносы строк `<w:br/>` в одном абзаце. Отклонена: ломает отступы нумерованного списка.

### 5. Поле «Номера запросов ЦБ»
- `FormField request_number` → label «Номера запросов ЦБ», placeholder «REQ-…, REQ-…».
- Разбор в генераторе: split по запятой/`;`/пробелам, trim, верхний регистр, порядок сохраняется, дубли
  убираются.
- `{{REQUEST}}` = `', '.join(reqs)`.
- JS при выборе пользователя: если поле пусто или равно предыдущему автозаполнению, подставить все его REQ из
  `obdsReqByUser`. REQ берутся и из записей, и из решений: решение могли загрузить раньше, чем заполнили
  переводы.

### 6. Приложения при экспорте
`build_document` получает в `params` список приложений (REQ, имя, байты), подготовленный view: решения
пользователя по REQ из поля, по порядку. Генератор строит `{{APPENDIX}}` и возвращает документ.

Затем view:
- **PDF:** `docx_to_pdf` → `pypdf.PdfWriter`, к нему добавляются страницы обращения и каждого решения. Битый
  PDF решения → ошибка «Не удалось прочитать решение ЦБ по REQ-…» и redirect, без тихого пропуска.
- **Word:** при наличии приложений — `zipfile` в памяти:
  - `Запрос_данных_ОБДС_<Фамилия>_<дата>.docx`;
  - `Приложение_1_REQ-….pdf`, …

  Без приложений — `.docx`, как раньше.

### 7. Зависимость
`pypdf` (чистый Python, без системных пакетов). Ставится в venv сервера и пинуется в `requirements.txt`.
`requirements.txt` в UTF-16: правим с сохранением кодировки.

## Risks / Trade-offs

- [Зашифрованный или нестандартный PDF решения не склеится] → явная ошибка, Word/ZIP по-прежнему работает.
- [Размер склеенного PDF при многих решениях] → лимит 20 МБ на файл, решений единицы.
- [S3 недоступен] → ошибка скачивания или экспорта показывается в сообщении, документ без приложений не
  отдаётся, чтобы банку не ушёл неполный пакет.
- [Опечатка «от отказе» в шаблоне Максима] → исправляем на «об отказе» в строке приложения и сообщаем.

## Migration Plan

1. Локально:
   - `makemigrations orders` (`ObdsDecision`, `ObdsRecord.attachment`/`attachment_name`);
   - подготовить шаблон с `{{APPENDIX}}`, сверить текст;
   - локальные тесты генератора и склейки (pypdf в локальный venv).
2. Деплой с подтверждения: `pip install pypdf` в venv сервера, `git pull`, `migrate orders`, restart `p2p`.
3. Проверка на проде с разрешения владельца:
   - тестовые файлы у `maks`: загрузка решения и PDF записи, экспорт PDF/ZIP, удаление;
   - всё тестовое удаляется и из БД, и из S3.
4. Откат: revert, `migrate orders 0048`. Новые таблица и поля на старые данные не влияют.
