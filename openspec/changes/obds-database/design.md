## Context

Мотивация описана в proposal.md, требования — в specs/obds-database/spec.md. Страница «Документооборот»
(`admin_documents`, `custom_admin/documents.html`) уже есть: GET-форма документов, поиск пользователя через
`datalist`, сообщения через `messages`. Записи ОБДС — новая сущность, связи с ордерами нет.

## Goals / Non-Goals

**Goals:**
- Минимальный учёт: одна таблица записей на пользователя, CRUD в той же странице без отдельных экранов.
- REQ из базы подсказывается в форме «Запрос данных по ОБДС».

**Non-Goals:**
- Импорт из файлов, выгрузка в Excel, статусы рассмотрения, привязка к ордерам — пока не просили.
- Доступ трейдеров к своим записям.
- Справочник банков или валидация идентификатора (БИК и т.п.): формат идентификатора не оговорён, поле —
  свободный текст.

## Decisions

### 1. Модель `ObdsRecord`
Поля:
- `user` — FK на `User`, `on_delete=CASCADE`, `related_name='obds_records'`;
- `req_number`, `sender_bank_id`, `receiver_bank_id` — `CharField(100)`;
- `sender_bank`, `receiver_bank` — `CharField(255)`;
- `amount` — `DecimalField(14, 2)`;
- `created_at` — `auto_now_add`.

Индекс по `(user, req_number)`. REQ хранится колонкой в каждой записи, без отдельной сущности «запрос» — так
решил владелец. Группировка по REQ — просто сортировка: `user`, `req_number`, `created_at`.

Альтернатива — модель `ObdsRequest` с FK от записей. Отклонена: лишний шаг в интерфейсе, владелец выбрал колонку.

### 2. Один view для всех операций
`admin_obds` принимает только POST и действие `add` / `update` / `delete`, затем делает redirect обратно на
`/admin-panel/documents/?obds_user=<id>#obds`. Отображение блока — в существующем `admin_documents`: параметр
`obds_user` выбирает пользователя. Отдельной страницы нет, Максим просил «ниже» на той же.

- Ошибка валидации → `messages` (отдельный тег `obds`, чтобы не смешивать с ошибками формы документов), а
  введённые значения кладутся в сессию на один показ.
- Удаление подтверждается через `confirm()` в браузере.
- Правка — та же форма в строке таблицы: кнопка «✏️» превращает строку в инпуты, JS без библиотек.

### 3. Сумма
Парсинг: убрать пробелы и NBSP, запятую заменить на точку, перевести в `Decimal`, значение должно быть > 0,
округление `ROUND_HALF_UP` до копеек. В шаблоне — формат `1 234,56 ₽` и итог по пользователю (по всем REQ).

### 4. Подсказки REQ в форме документа
Во view `admin_documents` собирается словарь `{user_id: [уникальные REQ]}` по всем записям одним запросом
`values_list('user_id', 'req_number').distinct()` и передаётся в шаблон через `json_script`. Поле
`f_request_number` получает свой `datalist`. JS при смене пользователя (событие `input` поиска, уже есть)
перестраивает его options. Объём маленький: записей единицы или десятки на пользователя.

### 5. Разделение двух поисков пользователя на странице
У блока ОБДС свой поиск пользователя (тот же паттерн `datalist` + hidden id) и своя GET-форма
(`obds_user`). Так выбор в форме документов и в базе ОБДС не мешают друг другу. Общая функция JS переиспользуется
для обоих полей.

## Risks / Trade-offs

- [Опечатки в REQ дают «разные» номера в подсказках] → правка записи доступна. REQ при сохранении обрезается от
  пробелов и переводится в верхний регистр.
- [Удаление необратимо] → `confirm()`. Записи — учётные данные админа, не фискальные.
- [Строка с инпутами на узком экране] → таблица в `overflow-x:auto`, как в других админских таблицах.

## Migration Plan

1. `makemigrations orders` (новая модель), миграция коммитится вместе с кодом.
2. Деплой с подтверждения владельца: `git pull` → `migrate orders` → restart `p2p`.
3. Проверка на проде через test Client:
   - блок рендерится;
   - добавление, правка и удаление тестовой записи у тестового/своего пользователя с удалением в конце —
     только с разрешения владельца (это запись в БД);
   - подсказки REQ приходят в JSON.
4. Откат: revert и `migrate orders 0047`. Таблица новая, на другие данные не влияет.
