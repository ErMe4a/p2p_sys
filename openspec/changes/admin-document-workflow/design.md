## Context

Мотивация описана в proposal.md, требования — в `specs/`.

Текущее состояние:
- Админ-панель — набор server-rendered страниц в `orders/views.py`. Все они закрыты
  `@user_passes_test(lambda u: u.is_superuser, login_url='admin_login')`, а навигация лежит в
  `custom_admin/admin_base.html`.
- Похожий прецедент — «Карточка предприятия» (`company_card_pdf.py` + `admin_export_company_card`): данные
  из `/settings/`, файл формируется в памяти и отдаётся как вложение.
- Все нужные поля профиля, кроме пола, уже есть: `last_name`, `first_name`, `middle_name`,
  `registration_address`, `phone`, `email`.
- Шаблон Максима — обычный `.docx` из Word: А4, одна таблица-шапка, колонтитул «Страница N из M». Заглушки
  выделены жёлтой заливкой и лежат в отдельных runs. Часть заглушек — это кусок слова: «принимал**а**»,
  «удостовери**лся**».
- На сервере установлены `openpyxl` и `reportlab`, `python-docx` нет.

## Goals / Non-Goals

**Goals:**
- Документ дословно повторяет шаблон Максима (шрифты, отступы, колонтитул), меняются только поля.
- Новую форму можно добавить, не трогая страницу: описать её поля и положить свой шаблон.

**Non-Goals:**
- Отправка заявления в ЦБ, подпись, хранение истории сформированных файлов.
- Доступ трейдеров к разделу (только админка).
- Редактирование текста заявления из интерфейса (меняется только заменой файла шаблона).
- Склонение ФИО по падежам («От Иванова Ивана…»). В шаблоне стоит именительный падеж, так и оставляем.

## Decisions

### 1. Заполнение `.docx` через `zipfile` и замену токенов в `word/document.xml`, без новых пакетов
В репозиторий кладётся **подготовленная копия** шаблона: `orders/doc_templates/cb_161fz_primary.docx`.
Жёлтые заглушки в ней заменены на токены в одном run и без жёлтой заливки:
- `{{FIO}}`, `{{ADDRESS}}`, `{{PHONE}}`, `{{EMAIL}}`, `{{DATE}}`, `{{FIO_SHORT}}`;
- `{{EXCHANGE}}`, `{{RULES_URL}}`;
- окончания: `{{A}}` («зарегистрирован/а», «принимал/а», «исполнил/а» → `''`/`'а'`) и `{{ASSURED_END}}`
  («удостовери/лся|лась»). При реализации токены поставлены на окончание, а не на слово целиком: основа слова
  уже лежит в соседнем run шаблона, так шаблон меньше отличается от оригинала. Проверка «текст вне токенов
  совпадает с оригиналом» пройдена.

Генератор открывает zip, в `word/document.xml` заменяет токены на XML-экранированные значения и пакует
обратно в память.

Альтернативы:
- **`python-docx`** — новая зависимость на сервере. В шаблоне с токенами в одном run она ничего не даёт.
- **Генерация с нуля** (reportlab или ручной XML) — потеряем точную вёрстку Максима, а текст придётся
  дублировать в коде.
- **Поиск жёлтых runs прямо в оригинале** — хрупко. Заглушки внутри слов, Word может разбить их на
  несколько runs при любой правке файла.

Подготовка копии — разовый скрипт (или ручная правка), её результат коммитится. В коде есть проверка: в
итоговом XML не осталось `{{…}}`, иначе ошибка, а не тихо испорченный документ.

### 2. Описание форм — реестр в коде
Модуль `orders/documents/` хранит реестр `FORMS = {key: Form(...)}`. Для каждой формы: человекочитаемое
название, файл шаблона, список обязательных полей профиля, дополнительные поля формы (у ЦБ-заявления —
биржа, ссылка, дата) и функция, которая строит словарь токенов. Страница рисует список форм из реестра,
поэтому вторая форма — это ещё одна запись и ещё один `.docx`. Хранить формы в БД сейчас избыточно: их
одна-две, а меняет их разработчик.

### 3. Биржа и дата — константы, без полей в форме
Изначально биржа выбиралась из каталога `Exchange`, а ссылка на правила и дата были редактируемыми полями. После
первого выката Максим решил, что заявление формальное: биржа всегда Bybit, дата — день формирования. Теперь
`{{EXCHANGE}}`/`{{RULES_URL}}` заполняются константами модуля, `{{DATE}}` — `timezone.localdate()` в момент
запроса. Токены в шаблоне оставлены: если биржа снова станет выбираемой, менять нужно только код, шаблон
трогать не придётся.

### 4. Пол — `User.gender`, `CharField(max_length=1, choices=[('M','Мужской'),('F','Женский')], blank=True, default='')`
Пустое значение по умолчанию: миграция не трогает существующие данные. В `/settings/` выпадающий список
рядом с ФИО («не указан / Мужской / Женский»), в `profile_settings` поле сохраняется так же, как соседние.
Автоопределение по отчеству отклонено по решению владельца: нужно явное поле.

### 5. Ошибки и UX страницы
Страница — GET-форма (`user_id`, `form`) с кнопкой «Сформировать».
Экспорт — отдельный URL. При нехватке данных он отдаёт не JSON, а redirect обратно на страницу
«Документооборот» с параметрами формы и сообщением через Django `messages`. Так админ видит список полей
на привычной странице, а не сырой JSON. Имя файла:
`Первичное_заявление_ЦБ_161-ФЗ_<Фамилия>_<ДДММГГГГ>.docx`, в `Content-Disposition` с `filename*=UTF-8''…`
(кириллица).

## Risks / Trade-offs

- [Word может «съесть» токен, разбив его на runs при будущей правке шаблона] → правится только подготовленная
  копия, а проверка «не осталось `{{`» и проверка «каждый токен был найден» сразу сломают формирование с
  явной ошибкой. Порядок правки шаблона описан в docstring генератора.
- [85+ трейдеров без заполненного пола и адреса прописки] → документ для них не формируется, админ видит, что
  дозаполнить. Дефолтов не подставляем.
- [Кириллица в имени файла в старых браузерах] → `filename*` RFC 5987 плюс ASCII-fallback `filename=`.

## Migration Plan

1. Локально `makemigrations orders` (поле `gender`), миграция коммитится вместе с кодом.
2. Деплой: `git pull` → `python manage.py migrate orders` → `sudo systemctl restart p2p`. Celery не
   затрагивается.
3. Проверка: страница открывается под суперпользователем. Формирование для одного трейдера с полным
   профилем (read-only) проверяется на сервере через `django.test.Client` + `force_login`. Подстановки и
   отсутствие токенов проверяются распаковкой `word/document.xml`.
4. Откат: revert коммита. Миграция с одним nullable/blank-полем откатывается `migrate orders <prev>` или
   остаётся безвредной.
