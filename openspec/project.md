# p2p_sys — project.md

Django-бэкенд (mininp2p.ru), трекает P2P крипто-ордера трейдеров (Bybit, MEXC, HTX, Gate, BingX, Telegram и др.),
верифицирует их через API биржи и фискализирует как чек через Evotor/Atol. Плюс налоговая отчётность (НДС,
уведомления) и админ-панель для оборота/прибыли. Компаньон — Chrome-расширение `minin-p2p/` (Manifest V3),
отдельный JS-проект, скрейпит данные со страниц бирж и шлёт их в REST API бэкенда.

## Стек

- **Backend:** Django 5.2.9 + Django REST Framework 3.16.1, Python (venv в репозитории).
- **БД:** PostgreSQL (`psycopg2-binary`), продакшен через `DATABASE_URL`.
- **Очереди/фон:** Celery 5.6.2 + Redis (broker), `django_celery_beat` — периодика настраивается в БД/админке, не в коде.
- **Биржевые интеграции:** `bybit_p2p` (vendored-копия пакета в корне репо — теневой приоритет над `venv/`), `pybit`, самописный REST-клиент для MEXC (`mexc_api.py`/`mexc_service.py`).
- **Файлы/медиа:** локально по умолчанию; S3 (Yandex Cloud, `django-storages`/`boto3`) — если заданы AWS-переменные.
- **Отчёты:** `openpyxl` (Excel), самописная генерация XML для НДС/уведомлений (`nds_generator.py`, `uvedomlenie_generator.py`).
- **Прод-сервер:** gunicorn + systemd (`p2p.service`, `celery.service`, `celery-sync.service`, `celery-receipt.service`, `celerybeat.service`), nginx перед ним. Деплой — `git pull` → `migrate` → `restart`, вручную по SSH, без CI/CD.
- **Фронтенд:** серверный Django-темплейтинг + Bootstrap 5.3 (тёмная/светлая тема через `data-bs-theme` + CSS-переменные) + ванильный JS (без сборщика/фреймворка).
- **Расширение (`minin-p2p/`):** Chrome Manifest V3, ванильный JS, отдельные content-скрипты на биржу (`content.js`=Bybit, `mexc.js`, `htx.js`, `gate.js`, `bingx.js`), общий `auth.js`/`order_api.js` для связи с бэкендом.
- Тестов нет (`orders/tests.py` — пустой шаблон), линтера/CI нет — единственная проверка перед деплоем: ручной прогон.

## Архитектура (фактическая структура папок)

```
core/                    # Django-проект: settings.py, urls.py (роутинг: '' → orders.urls, 'api/' → orders.api_urls), celery.py
orders/                  # единственное Django-приложение — вся бизнес-логика тут
  models.py              # User(AbstractUser), Order, BankDetail, Exchange, UnprocessedOrder, IgnoredOrder,
                          #   MonthlyManualEntry, BalanceCorrection, DocumentSubmission, OrderScreenshot
  views.py                # ~3900+ строк: юзер-вьюхи (мои ордера/настройки/прибыль/ФНС) + вся кастомная админка
                          #   в одном файле — искать по имени функции, не читать целиком
  api_views.py            # DRF-эндпоинты для расширения (TokenAuth/Bearer, orders/authentication.py)
  urls.py / api_urls.py   # роуты для серверного HTML и для REST API соответственно
  tasks.py                # Celery-задачи: sync_*_orders_task (fan-out по юзерам), verify_and_receipt_later
                          #   (ретраи верификации до ~48ч), retry_blocked_orders_task, recheck_mexc_keys_task,
                          #   recompute_fns_status_task
  bybit_api.py / mexc_api.py         # персистентный sync-путь (пишет в UnprocessedOrder/Order)
  bybit_service.py / mexc_service.py # параллельный read-only путь для live-вьюх админки (ничего не пишет)
  exchange_api.py         # единая точка верификации ордера через API биржи (Bybit/MEXC, авторитетный источник)
  receipt_service.py + evotor_atol.py # сборка и отправка чека в Evotor/Atol v5
  nds_generator.py / uvedomlenie_generator.py # налоговые XML-документы
  migrations/             # 36 миграций, актуальная схема — до 0036 (MonthlySystemProfitSummary, кэш годовой прибыли)
  templates/
    orders/               # юзер-фронт: my_orders, settings, profit, fns, unprocessed (extends base.html)
    custom_admin/         # кастомная админка: users_list, profit_list, profit_year, orders_editor,
                          #   turnover_control, statistics_24, fns_documents, catalog, login, admin_base.html
    registration/login.html
bybit_p2p/                # vendored-копия пакета bybit_p2p — правки биржевого клиента вносятся ЗДЕСЬ, не в venv/
minin-p2p/                 # Chrome-расширение (отдельный JS-проект), версия 1.5.0
openspec/                  # spec-driven workflow (эта система), history.md — копия SESSION_LOG.md
venv/                       # виртуальное окружение (закоммичено в репо)
CLAUDE.md, AUDIT_PLAN.md, SESSION_LOG.md  # ручная документация проекта и лог сессий
```

**Два независимых пути получения ордеров с биржи** — не путать: `bybit_api.py`/`mexc_api.py` (периодический sync,
пишет в БД) vs `bybit_service.py`/`mexc_service.py` (параллельный live-запрос для админки, ничего не сохраняет).

**Инвариант фискализации:** чек уходит только по `is_verified=True` (подтверждено API биржи) или `is_manual=True`
(осознанный ручной ввод) — фолбэк на непроверенные данные расширения запрещён и физически убран из кода.

## Текущий статус приложения

**Стабильно работает и в проде:** синк Bybit/MEXC, верификация + автофискализация чеков (для Bybit/MEXC — через
API; для остальных бирж — по ручному вводу), валюта ордера (USDT/TON/BTC) для Bybit/MEXC теперь тоже определяется
через API биржи (`tokenId`/`coinName`), не только с расширения — включая ручное редактирование на Bybit (дропдаун
"Валюта" убран, см. history.md §43.1), НДС/уведомления (вкл. порог 20 млн для УСН), светлая/тёмная тема на всех
страницах, каталог банков/бирж (`custom_admin/catalog.html`, добавление/скрытие/переименование банков),
персональный выбор видимых банков/бирж на `/settings/`, вкладка «2026» в админ-«Прибыли» — **оборот И помесячная
грязная/чистая прибыль трейдеров/доход системы** по всем юзерам сразу (фоновый кэш, `MonthlySystemProfitSummary`,
пересчёт раз в час, см. `openspec/changes/add-monthly-profit-breakdown` — change закрыт технически, задачи
выполнены, архивация не запрошена). Приватность банков/бирж (`BankDetail.is_public`/`Exchange.is_public` +
`User.allowed_banks`/`allowed_exchanges`) — админ в каталоге переключает банк/биржу в приватный статус и через
живой поиск добавляет, кому конкретно видно; `/settings/` показывает и разрешает выбирать только доступное
(см. history.md §44.2). Прод-сервер апгрейжен до 4 vCPU / 8 ГБ RAM (был 2/4). Производительность: `/profit/`
трейдера (~0.9с) и особенно админ-«Прибыли» (было 21.5с → стало **0.1–0.5с**, через фоновый кэш
`MonthlyUserProfitCache`, наполняется раз в 15 минут `tasks.recompute_admin_profit_cache_task`) и ZIP-экспорт
скриншотов (параллельная загрузка из S3) — см. history.md §45.4/§45.5/§45.6.

**Расширение: версия 1.5.4 (поднята с 1.5.3 в этой сессии), гейт версии на бэкенде включён
(`orders/middleware.py`, принимает 1.5.2 и выше — не точное совпадение).** ⚠️ **Правки 1.5.4 (см. history.md §46.13)
закоммичены только локально — в git не запушены, задеплоены вручную Максу через zip-архив в чат, не обычным
деплой-циклом.** MEXC полностью переверстал страницы в августе 2026 — парсинг данных/замена имени контрагента под
новую вёрстку пофикшены (см. history.md §43.1 за деталями). "Своё имя" на MEXC по-прежнему не реализовано
технически (кнопка есть, эффекта нет) — только на Bybit. В 1.5.4 дополнительно: на HTX — дата ордера (3 раунда
фикса, теперь берёт самую раннюю дату из чата, а не текущий момент), никнейм контрагента, принудительное
переприменение подмены перед скриншотом; на Bybit — лейбл "Verified:"/"Подтверждён:" больше не стирается при
замене имени, подпись отправителя в сообщениях чата тоже подменяется; на MEXC — исправлен `ReferenceError` при
разлогине, подключена подмена "KYC Name"/"Имя КУС", хелпер поиска строк инфопанели (`getMexcInfoRowValueEl`)
теперь ищет и русские, и английские лейблы (раньше — только английские, реальный интерфейс у пользователей
русский), кнопка сброса имени контрагента реально заработала (раньше слала `resetCounterpartyNames`, которого
в коде не было вообще).

**Ждут решения (см. `openspec/history.md` §43/§44/§45 за подробностями каждого):**
- Январский Excel-импорт (`orders.management.commands.import_january_excel`) — 72 из 93 файлов трейдеров загружено
  (31 732 сделки), 19 без опознанного логина, 1 (`gamzatov`) ждёт файл от Макса, 1 (`hahin`/`khakhin`) — реально
  битые цифры внутри файла. У импортированных 72 теперь январь корректно виден построчно в Excel-отчёте
  (`export_excel_report`), см. §45.2 — но строка "Остаток (до 1 фев)" по-прежнему не пересчитана и может не
  сходиться с фактом у тех, кому январь ещё НЕ импортирован (не проверялось системно, только на kolosov).
- LIFO-расчёт прибыли на `/profit/` может немонотонно "проседать" при новой продаже (пересчёт остатка целиком на
  каждый запрос) — итоговая цифра за месяц верна, но живая цифра на экране скачет; алгоритм не переделывался.
  Родственная проблема того же класса — `_calc_currency_from_orders` (её использует помесячная вкладка `/profit/`,
  action `get_months`) считает комиссию биржи в рублях по курсу **последнего** ордера месяца, а не по курсу каждого
  отдельно — один аномальный ордер может исказить комиссию всего месяца на порядки (живой случай: rodionov, §44.1,
  1.2 млн ₽ вместо ~250 ₽). Код не переделывался, обе проблемы решаются одним и тем же архитектурным вопросом.
- `retry_blocked_orders_task` перепробивает только `is_verified=False` — верифицированные ордера, у которых
  единственная попытка отправки чека сорвалась, никогда не подхватываются автоматически (живой случай, всё ещё
  открыт: egizbaev — 3 висящих Bybit-чека, майские/июньские/июльские, ждут подтверждения; olkhovikov, pyrkh и
  ещё один ордер egizbaev от 27.08 — уже пофикшены вручную, см. §44.4/§45.1). Системный фикс не сделан.
- eldarov — решено (см. history.md §46.12): "отрицательный остаток" объяснялся не отсутствием входного баланса,
  а 25 ордерами с перепутанным местами `operation_type` (BUY↔SELL) относительно данных самой биржи —
  исправлено, LIFO пересчитан и адекватен. akhmedov — решено (§46.4, задержка применения новой ставки
  Telegram-комиссии на ~3 дня в начале августа). podkolzin — проверено, не баг (§46.5, легитимное разовое
  переключение ставки).
- **Чеки коррекции Эвотора не реализованы** (архитектура набросана, history.md §46.6, но код не писался — нужно
  сначала подтвердить схему v5 API у поддержки Эвотора). Уже есть минимум два живых кандидата, где это нужно:
  mirzakhanov (ордера 334652/336027, §46.9) и все 25 ордеров eldarov из §46.12 — по всем чек уже реально
  отправлен (`status=SENT`) с перепутанными местами полями (`sum`/`price` или `operation_type` sell/buy), то
  есть в ФНС уже поданы фискальные документы с неверными данными; правка в нашей БД это не чинит.
- golev — 4339 ордеров в «Необработанных» за всё время (620 покупок/3719 продаж), из-за чего реальные покупки на
  MEXC не долетают до системы и остаток на `/profit/` может уходить в глубокий минус (живой случай — август,
  −10 288 USDT, см. §44.3). Решение не принято: либо трейдер сам регулярно разгружает список, либо нужен
  админский инструмент массового подтверждения таких ордеров.
- Баг округления в самом чеке (`evotor_atol.py` округляет цену вниз, не к ближайшему) — Эвотор сам "чинит",
  раздваивая позицию на две строки с разными ценами; на прибыль не влияет, чисто визуально на бумаге.

**Известные незакрытые проблемы (см. `openspec/history.md` для деталей):**
- Отправка чека при мгновенной верификации Bybit/MEXC — синхронный вызов внутри HTTP-запроса от расширения, без
  единого ретрая при сбое Evotor; ответ API всегда `success:true` независимо от статуса чека — расширение эту
  ошибку не показывает пользователю.
- Ручная форма "Мои ордера" не валидирует дату (`created_at`) вообще никак — уже приводило к ордерам с датой
  в следующем месяце, искажающим отчётность, а форма ещё и не сбрасывает поле даты между вводами (подставляет
  прошлое значение) — при быстром вводе многих ордеров подряд легко потерять фокус между ячейками
  день/час нативного `datetime-local`-виджета и получить дату из прошлого месяца (живой случай: mirzakhanov,
  4 ордера с "01" вместо "31", history.md §44.5).
- Ордера, созданные через ручную форму, никогда не получают `is_manual=True` — из-за этого при сбое отправки чека
  для них нет вообще никакого автоматического пути повтора (ни verify-ретраев, ни recheck-задач). Живые
  подтверждения: golev (топ-ордера is_verified=False, но чек SENT) и asadulaev (48 ордеров без единой попытки
  чека, т.к. форма отправляет чек только если явно отмечена галочка) — см. history.md §44.3/§44.6.
- Поиск юзера по логину через `username__icontains` — риск попасть не на того при похожих логинах (живой инцидент:
  `salatgereev`/`salatgereev_adam`/`salatgereev_isa` — правка комиссии по ошибке улетела не туда, поймано и
  откачено сразу, см. history.md §44.7). Искать точным `username=`, если не уверен, что логин уникален.
- **`celery.service`/`celerybeat.service` были `disabled`** (не автозапускались после ребута) — обнаружено только
  при плановом ресайзе сервера 04.09.2026, неизвестно с какого момента это так было. Без celerybeat не срабатывает
  ни один периодический таск (синк бирж, ретраи верификации, кэши прибыли) — тихий отказ. Поправлено
  (`systemctl enable --now`), но стоит иметь в виду при любом будущем перезапуске/миграции сервера — проверять
  `systemctl is-enabled` на все 8 сервисов, не только `is-active`. См. history.md §45.3.
- Кэш `MonthlyUserProfitCache` (admin-«Прибыли», см. §45.5) — сознательный компромисс: цифры устаревают до
  15 минут после правки ордера задним числом (а таких правок за сессию бывает много). Пересчитать раньше срока —
  вручную вызвать `tasks.recompute_admin_profit_cache_task()`.
- Расширение (`minin-p2p/auth.js`) при HTTP 403 от бэкенда, не подошедшем под известные текстовые шаблоны, всегда
  трактует это как "истекла сессия" и разлогинивает юзера — маскирует настоящую причину (например, невалидный
  биржевой ключ) понятным, но неверным сообщением.
- На странице «Прибыль» трейдера (`profit.html`) кнопка вкладки называется "За текущий месяц", но реально считает
  строго один день (id/логика — `today`) — название разошлось с поведением из-за случайной правки в чужом коммите
  (см. history.md §41). Не исправлено, ждёт решения.
- На той же вкладке карточки "Покупки/Продажи" считаются за выбранный день, а карточки "Прибыль" — всегда за весь
  текущий календарный месяц, независимо от выбранного диапазона дат — архитектурная особенность (не баг), сбивает
  трейдеров с толку (см. history.md §42, инцидент sedurin). Решение, как это должно работать, не принято.
- Ручной ввод комиссии на форме "Мои ордера" не защищён от смешения "комиссия банка" и "комиссия биржи" в голове
  трейдера (валидация ловит только явно нелепые значения >5%, не сам факт подмены поля) — см. history.md §42,
  реальный инцидент на 307 ордерах одного юзера.
- Несколько открытых вопросов по конкретным пользователям/документам (импорт январских сделок из Excel, дата
  регистрации ИП для расчёта периода НДС) — решения ждут ответа от Макса.
- `build_receipt_payload_v5` доверяет `receipt_data.get("sum")`/`.get("price")` от вызывающего кода (форма/
  расширение) вместо данных самого `order`, если они не нулевые — если форма передаёт перепутанные местами поля,
  это уходит в реальный фискальный чек без проверки. Живое подтверждение: mirzakhanov, ордера 334652/336027
  (см. history.md §46.9) — уже отправленные чеки с перепутанными `sum`/`price`. Не исправлено.
- Расширение MEXC (`findCounterpartyHeaderButton()` в `mexc.js`) перестаёт находить кнопку шапки чата при узкой
  ширине окна браузера (проверено — ломается уже при ~950px) — адаптивная вёрстка меняет структуру DOM. Замена
  имени контрагента в шапке в этом случае молча не срабатывает. Не исправлено, см. history.md §46.13.
